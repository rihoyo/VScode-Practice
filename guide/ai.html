2. 기초로 알아둘 것

에이전트 루프

에이전트는 한 번 답하고 끝나지 않고 목표 → 읽기 → 계획 → 실행 → 확인을 목표가 달성될 때까지 되풀이한다. 실행은 도구(파일 읽기, 파일 수정, 명령 실행, 검색, MCP로 붙인 외부 서비스)를 부르는 일이다.

목표→읽기→계획→도구 실행→결과 확인↺ 달성할 때까지
  1. 모델과 하네스를 구분한다. 모델은 생각하는 두뇌고, 하네스는 그 둘레의 도구, 권한, 지시문, 검증 장치다. 같은 모델도 하네스가 다르면 결과가 크게 달라진다. 심화에서 자세히 다룬다.
  2. 토큰과 컨텍스트를 안다. 모델이 한 번에 보는 글의 양이 컨텍스트 창이고 글자 수는 토큰으로 센다. 대화, 읽은 파일, 명령 출력이 모두 여기에 쌓이고, 가득 차 갈수록 비용이 늘고 앞부분을 놓치기 쉽다.
  3. 권한을 안다. 파일 수정과 명령 실행은 기본적으로 허락을 받고 한다. 허락을 줄수록 빠르지만 위험도 커진다.
  4. 검증은 사람의 몫이다. 에이전트가 "됐다"고 말하는 것과 실제로 되는 것은 다르다. 테스트, 린트, git diff로 직접 확인한다.

먼저 익혀 두면 좋은 개발 기초

  • 터미널: cd, ls, 경로 읽기. 리눅스에서 연습한다.
  • Git: 브랜치, git diff, 커밋. 에이전트가 만든 변경은 반드시 diff로 본다. Git 페이지를 본다.
  • 테스트와 린트: 에이전트에게 "끝났는지 어떻게 알 수 있나"를 알려 주는 기준이다.
  • 비밀값: .env, 키, 토큰은 저장소에 넣지 않고 에이전트에게 붙여 넣지 않는다.
  • 코드 읽기: 쓰지는 못해도 읽을 수 있어야 맡긴 결과를 판단한다.

4. 실무에서 쓰는 법

실무의 기본 흐름은 탐색 → 계획 → 구현 → 검증 → 리뷰 → 정리다. 처음부터 구현을 시키지 않고, 먼저 읽고 계획만 내게 한 뒤 사람이 방향을 고친다. 이때 Claude Code의 plan 모드나 Codex의 읽기 전용 샌드박스를 쓰면 코드가 바뀔 걱정 없이 탐색할 수 있다.

상황이렇게 시킨다사람이 확인할 것
버그 수정재현 방법과 실패하는 테스트를 주고 "테스트가 통과하게 고쳐라"원인이 맞는지, 테스트를 지워서 통과시키지 않았는지
기능 추가계획을 먼저 받고 승인한 뒤 작은 단위로 구현범위 밖 파일 변경이 없는지
리팩터링동작을 바꾸지 않는다는 제약과 기존 테스트를 준다테스트 전후 결과가 같은지
테스트 작성대상 함수와 경계 조건 목록을 준다테스트가 실제로 실패할 수 있는지(코드를 일부러 깨 본다)
코드 리뷰브랜치를 주고 버그와 위반만 보고하게 한다지적이 진짜인지(거짓 양성을 걸러 낸다)
새 저장소 파악"구조, 실행 방법, 테스트 방법을 요약해라"요약을 실제 파일과 맞춰 본다
반복 작업claude -p, codex exec를 CI나 스크립트에서 돌린다권한을 최소로 주었는지
  • 작게 맡긴다. 한 세션에 한 가지 일만 시키고, 끝나면 대화를 정리한다.
  • 브랜치나 워크트리에서 돌린다. 잘못되면 버리면 되도록 main에서 시키지 않는다.
  • 사람이 쥐는 것: 비밀값, 배포 승인, 데이터 삭제, 설계 결정. 이 넷은 에이전트에게 넘기지 않는다.
  • 커밋은 작게, 자주. 마스터가 직접 커밋과 푸시를 연습하는 동안에는 에이전트에게 커밋하지 말라고 지시문에 적어 둔다. 이 저장소의 방식이다.

5. 심화: 컨텍스트

컨텍스트는 모델이 지금 이 순간 눈앞에 두고 있는 글 전체다. 시스템 지시, 도구 설명, 지시문 파일(CLAUDE.md, AGENTS.md), 대화, 읽은 파일, 명령 출력이 모두 들어간다. 창은 유한해서 가득 차면 오래된 내용이 밀리거나 요약된다.

무엇이 쌓이나특징줄이는 법
고정 부분(시스템, 도구 정의)매번 들어가고 줄일 수 없다. MCP 서버를 많이 붙일수록 커진다.안 쓰는 MCP 서버를 끈다
지시문 파일세션마다 처음에 읽힌다. 길수록 매번 비용이 든다.짧게 유지하고 자세한 내용은 파일 경로로 가리킨다
읽은 파일한 번 읽으면 계속 남는다.필요한 줄 범위만 읽게 한다
명령 출력테스트 로그 전체가 들어오면 크다.실패한 줄만 보게 하고 출력을 잘라 준다
대화턴이 쌓일수록 늘어난다.일이 바뀌면 /clear(/new), 길어지면 /compact

세 가지 도구

  1. 압축(/compact): 지금까지의 대화를 요약해 자리를 비운다. 같은 일을 이어 갈 때 쓰고, 요약에서 세부가 빠질 수 있다.
  2. 초기화(/clear, Codex는 /new): 대화를 비우고 처음부터 다시 시작한다. 일이 바뀔 때 쓴다. 지시문 파일은 새로 읽힌다.
  3. 분리(서브에이전트): 큰 탐색을 다른 에이전트에게 맡기고 요약만 받는다. 읽은 파일 수십 개가 내 컨텍스트에 쌓이지 않는다. 실습 5에서 숫자로 본다.

컨텍스트가 80%를 넘기면 지시를 놓치거나 같은 실수를 되풀이하기 쉽다. 이 신호가 보이면 압축하거나 새로 시작한다. 실습 2에서 직접 채워 본다.

6. 심화: 하네스

하네스는 모델을 둘러싼 모든 것이다. 모델에게 무엇을 보여 주고(컨텍스트), 무엇을 할 수 있게 하고(도구), 어디까지 허락하고(권한·샌드박스), 어떻게 확인하게 할지(검증)를 정한다. 같은 모델이라도 하네스가 좋으면 잘 쓰고, 나쁘면 같은 실수를 되풀이한다.

설계 원칙

  1. 권고와 강제를 나눈다. 지시문은 부탁이라 어길 수 있다. 꼭 지켜야 하는 것(비밀 파일 접근 금지, 검사 실행)은 권한 규칙이나 훅으로 막는다.
  2. 피드백 고리를 만든다. 에이전트가 스스로 틀렸음을 알 수 있어야 한다. 검사 명령 하나(npm run check)를 정하고, 수정할 때마다 돌리게 한다.
  3. 작게 열고 필요하면 넓힌다. 처음에는 읽기만, 다음에는 작업 폴더 쓰기만 허락한다. 네트워크나 폴더 밖 쓰기는 마지막이다.
  4. 지시문은 짧게, 근거는 파일로. 규칙 열 줄이 규칙 백 줄보다 잘 지켜진다.
  5. 결과를 남긴다. 결정과 다음 단계를 파일(STATUS.md)에 적어 다음 세션이 이어받게 한다.

이 저장소의 하네스

마스터의 저장소가 좋은 예다. AGENTS.md가 규칙을 말하고(권고), CLAUDE.md는 그것을 가져오고, npm run check가 링크, 문체, 폰트, 지도 데이터를 기계로 검사하며(검증), STATUS.md가 진행 상황을 남긴다(결과 기록). 규칙만 적은 것이 아니라 어긴 것을 잡아 주는 장치가 있다는 점이 핵심이다.

// Claude Code: .claude/settings.json - 파일을 고칠 때마다 검사를 자동으로 돌린다
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm run check" }] }
    ]
  }
}

# Codex: ~/.codex/config.toml - 묻는 때와 닿는 범위를 따로 정한다
approval_policy = "on-request"
sandbox_mode    = "workspace-write"

7. 실습

명령어만 외우면 "개발자 노트에 왜 이런 게 적혀 있는지"를 알 수 없다. 아래 여섯 실습은 같은 요청을 설정 하나만 바꿔 돌려 보고, 무슨 일이 일어났는지, 무엇이 달라졌는지, 왜 해야 하는지를 보여 준다. 모두 이 페이지 안의 시뮬레이션이라 새로고침하면 처음으로 돌아가고 아무것도 저장되지 않는다.

실습 1지시문 한 줄이 결과를 바꾼다

같은 요청을 지시문 파일(CLAUDE.md/AGENTS.md)의 규칙만 바꿔 보낸다. 규칙을 켜고 끄면서 에이전트의 행동이 어떻게 달라지는지 본다.

왜 하나 지시문은 에이전트가 세션을 시작할 때 처음 읽는 규칙집이다. 매번 같은 말을 되풀이하지 않아도 되고, 사람이 바뀌어도 같은 방식으로 일하게 만든다. 규칙은 짧을수록 잘 지켜진다.

실습 2컨텍스트를 채우고 비운다

작업을 하나씩 추가해 컨텍스트가 차오르는 것을 보고, /compact와 /clear가 각각 무엇을 바꾸는지 눌러 본다. 숫자는 감을 잡기 위한 예시다.

왜 하나 컨텍스트가 가득 차면 느려지고 비싸지고, 앞에서 정한 규칙을 놓친다. 언제 압축하고 언제 새로 시작할지 아는 것이 긴 작업의 품질을 정한다.

실습 3권한 모드가 행동을 막고 푼다

같은 여섯 행동을 모드별로 돌려 본다. 어떤 행동은 그냥 지나가고, 어떤 행동은 허락을 구하고, 어떤 행동은 막힌다.

왜 하나 허락을 모두 열면 빠르지만 파일 삭제나 푸시도 그냥 지나간다. 모두 닫으면 안전하지만 매번 눌러야 한다. 일에 맞는 모드를 고르는 것이 하네스 설계의 시작이다. 이 표는 단순화한 모델이다.

실습 4훅과 검증이 실수를 되돌린다

에이전트가 오타가 든 수정을 했다고 하자. 검사 훅이 없을 때와 있을 때를 각각 재생해 결과를 비교한다.

왜 하나 "고쳤다"는 말은 증거가 아니다. 검사가 자동으로 돌고 실패가 에이전트에게 되돌아가야 스스로 고친다. 지시문의 "검사를 돌려라"는 부탁이고, 훅은 강제다.

실습 5서브에이전트로 컨텍스트를 아낀다

코드베이스에서 인증 코드를 찾는 탐색을 직접 할 때와 서브에이전트에게 맡길 때의 컨텍스트 사용량을 비교한다. 읽을 파일 수를 바꿔 본다.

왜 하나 탐색은 많이 읽고 조금만 남기는 일이다. 그 많은 읽기를 내 컨텍스트에 쌓을 필요가 없다. 요약만 받으면 본 작업에 쓸 자리가 남는다.

실습 6한 번만 실행해서 자동화한다

도구, 작업, 출력 형식, 권한 범위를 골라 claude -p와 codex exec 명령을 만든다. 각 부분이 무엇을 하는지 옆에 풀어 준다.

왜 하나 대화 없이 한 번 돌리면 CI, 스크립트, 예약 작업에서 쓸 수 있다. 사람이 없으니 권한은 최소로, 출력은 기계가 읽을 형식으로 정해야 한다.

8. 플랜별 기능

Claude는 구독에 Claude Code가 들어 있고, Codex는 ChatGPT 구독에 들어 있다. 플랜을 올릴수록 사용량, 모델, 속도, 협업·보안 기능이 열린다. 아래에서 도구와 플랜을 골라 무엇이 열리는지 본다.

10. 출처와 확인 방법

    이 페이지는 위 공식 페이지를 읽고 정리했다. 도구는 빠르게 바뀌므로 다음 순서로 직접 확인한다.

    1. 터미널에서 claude --version, codex --version으로 설치된 버전을 본다.
    2. 슬래시 명령은 /help로 지금 버전의 목록을 본다.
    3. 요금과 한도는 위 요금 페이지와 계정의 사용량 화면에서 본다.

    주석

    1. 이 페이지의 요금, 한도, 버전, 변경 기록은 2026-11-24에 공식 페이지(Claude 요금제, Claude Code 변경 기록, Codex 요금제와 변경 기록)를 읽고 정리했다. 일부 페이지는 길어서 일부만 읽었고, 읽히지 않은 값은 ?로 표시했다.
    2. 표의 슬래시 명령은 2026-11-24 점검 기준으로 정리했다. 마스터가 실제 화면에서 직접 확인하기 전까지는 확인 전이다.
    3. 요금과 한도는 2026-11-24에 공식 페이지를 읽고 정리한 값이다. 페이지에서 읽히지 않은 칸은 ?로 두었고, 한도는 고정 수치가 아니라 추정치다. 결제 전에 공식 요금 페이지에서 다시 확인한다.
    4. Claude Code 변경 기록에 적힌 예고다. 검색 결과에는 Opus 4.8 빠른 모드가 11-30에 제거된다는 내용도 있었지만 공식 페이지에서 확인하지 못해 확인 전으로 둔다.
