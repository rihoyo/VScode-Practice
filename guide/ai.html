2. 설치와 첫 실행

두 도구 모두 만든 회사의 공식 GitHub 저장소에 설치 방법이 있다. 설치는 명령 한 줄이고, 끝나면 버전을 확인한 뒤 프로젝트 폴더에서 실행해 로그인한다. 아래에서 운영체제를 고르면 그에 맞는 명령으로 바뀌고, 복사를 누르면 명령이 복사된다.

Claude CodeAnthropicGitHub 저장소설치 문서

  2. 확인claude --version터미널을 새로 연 뒤 실행한다. 성공하면 2.1.331 같은 버전 번호가 나온다. 문제가 있으면 claude doctor로 진단한다.
  3. 첫 실행claude프로젝트 폴더로 이동해서 실행하면 브라우저가 열리고 로그인을 요청한다. Pro 이상 구독이나 Console(API) 계정이 필요하고, 무료 플랜으로는 쓸 수 없다.
  4. 업데이트claude update권장 방식으로 설치했다면 백그라운드에서 자동으로 업데이트된다. 이 명령은 바로 올리고 싶을 때 쓴다.

설치 명령은 인터넷에서 받은 스크립트를 바로 실행한다. 주소가 claude.ai, chatgpt.com인지 확인하고, 블로그 등에 적힌 명령보다 위 공식 페이지의 명령을 복사한다.

3. 기초로 알아둘 것

에이전트 루프

에이전트는 한 번 답하고 끝나지 않고 목표 → 읽기 → 계획 → 실행 → 확인을 목표가 달성될 때까지 되풀이한다. 실행은 도구(파일 읽기, 파일 수정, 명령 실행, 검색, MCP로 붙인 외부 서비스)를 부르는 일이다.

목표→읽기→계획→도구 실행→결과 확인↺ 달성할 때까지
  1. 모델과 하네스를 구분한다. 모델은 생각하는 두뇌고, 하네스는 그 둘레의 도구, 권한, 지시문, 검증 장치다. 같은 모델도 하네스가 다르면 결과가 크게 달라진다. 심화에서 자세히 다룬다.
  2. 토큰과 컨텍스트를 안다. 모델이 한 번에 보는 글의 양이 컨텍스트 창이고 글자 수는 토큰으로 센다. 대화, 읽은 파일, 명령 출력이 모두 여기에 쌓이고, 가득 차 갈수록 비용이 늘고 앞부분을 놓치기 쉽다.
  3. 권한을 안다. 파일 수정과 명령 실행은 기본적으로 허락을 받고 한다. 허락을 줄수록 빠르지만 위험도 커진다.
  4. 검증은 사람의 몫이다. 에이전트가 "됐다"고 말하는 것과 실제로 되는 것은 다르다. 테스트, 린트, git diff로 직접 확인한다.

토큰 계산기

모델은 글을 글자 단위가 아니라 토큰이라는 조각으로 나눠 읽는다. 아래 칸에 글을 넣으면 OpenAI 모델이 쓰는 규칙으로 몇 토큰인지 세고, 조각마다 색을 칠해 어디서 끊기는지 보여 준다. 영어는 단어 하나가 대개 한 토큰이고, 한국어와 코드는 더 잘게 나뉘는 경우가 많다.

예시
0토큰
0글자
-글자당 토큰

칸에 글을 넣으면 계산을 시작한다.

이 계산기는 OpenAI 모델 기준이다. Claude는 토큰을 나누는 규칙이 달라서 같은 글도 숫자가 다르게 나온다. 정확한 값은 공식 OpenAI 토크나이저에서 확인한다. 계산은 이 PC의 브라우저 안에서만 하고, 넣은 글은 어디로도 보내지 않는다.

먼저 익혀 두면 좋은 개발 기초

  • 터미널: cd, ls, 경로 읽기. 리눅스에서 연습한다.
  • Git: 브랜치, git diff, 커밋. 에이전트가 만든 변경은 반드시 diff로 본다. Git 페이지를 본다.
  • 테스트와 린트: 에이전트에게 "끝났는지 어떻게 알 수 있나"를 알려 주는 기준이다.
  • 비밀값: .env, 키, 토큰은 저장소에 넣지 않고 에이전트에게 붙여 넣지 않는다.
  • 코드 읽기: 쓰지는 못해도 읽을 수 있어야 맡긴 결과를 판단한다.

5. 실무에서 쓰는 법

실무의 기본 흐름은 탐색 → 계획 → 구현 → 검증 → 리뷰 → 정리다. 처음부터 구현을 시키지 않고, 먼저 읽고 계획만 내게 한 뒤 사람이 방향을 고친다. 이때 Claude Code의 plan 모드나 Codex의 읽기 전용 샌드박스를 쓰면 코드가 바뀔 걱정 없이 탐색할 수 있다.

상황이렇게 시킨다사람이 확인할 것
버그 수정재현 방법과 실패하는 테스트를 주고 "테스트가 통과하게 고쳐라"원인이 맞는지, 테스트를 지워서 통과시키지 않았는지
기능 추가계획을 먼저 받고 승인한 뒤 작은 단위로 구현범위 밖 파일 변경이 없는지
리팩터링동작을 바꾸지 않는다는 제약과 기존 테스트를 준다테스트 전후 결과가 같은지
테스트 작성대상 함수와 경계 조건 목록을 준다테스트가 실제로 실패할 수 있는지(코드를 일부러 깨 본다)
코드 리뷰브랜치를 주고 버그와 위반만 보고하게 한다지적이 진짜인지(거짓 양성을 걸러 낸다)
새 저장소 파악"구조, 실행 방법, 테스트 방법을 요약해라"요약을 실제 파일과 맞춰 본다
반복 작업claude -p, codex exec를 CI나 스크립트에서 돌린다권한을 최소로 주었는지
  • 작게 맡긴다. 한 세션에 한 가지 일만 시키고, 끝나면 대화를 정리한다.
  • 브랜치나 워크트리에서 돌린다. 잘못되면 버리면 되도록 main에서 시키지 않는다.
  • 사람이 쥐는 것: 비밀값, 배포 승인, 데이터 삭제, 설계 결정. 이 넷은 에이전트에게 넘기지 않는다.
  • 커밋은 작게, 자주. 마스터가 직접 커밋과 푸시를 연습하는 동안에는 에이전트에게 커밋하지 말라고 지시문에 적어 둔다. 이 저장소의 방식이다.

6. 심화: 컨텍스트

컨텍스트는 모델이 지금 이 순간 눈앞에 두고 있는 글 전체다. 시스템 지시, 도구 설명, 지시문 파일(CLAUDE.md, AGENTS.md), 대화, 읽은 파일, 명령 출력이 모두 들어간다. 창은 유한해서 가득 차면 오래된 내용이 밀리거나 요약된다.

무엇이 쌓이나특징줄이는 법
고정 부분(시스템, 도구 정의)매번 들어가고 줄일 수 없다. MCP 서버를 많이 붙일수록 커진다.안 쓰는 MCP 서버를 끈다
지시문 파일세션마다 처음에 읽힌다. 길수록 매번 비용이 든다.짧게 유지하고 자세한 내용은 파일 경로로 가리킨다
읽은 파일한 번 읽으면 계속 남는다.필요한 줄 범위만 읽게 한다
명령 출력테스트 로그 전체가 들어오면 크다.실패한 줄만 보게 하고 출력을 잘라 준다
대화턴이 쌓일수록 늘어난다.일이 바뀌면 /clear(/new), 길어지면 /compact

세 가지 도구

  1. 압축(/compact): 지금까지의 대화를 요약해 자리를 비운다. 같은 일을 이어 갈 때 쓰고, 요약에서 세부가 빠질 수 있다.
  2. 초기화(/clear, Codex는 /new): 대화를 비우고 처음부터 다시 시작한다. 일이 바뀔 때 쓴다. 지시문 파일은 새로 읽힌다.
  3. 분리(서브에이전트): 큰 탐색을 다른 에이전트에게 맡기고 요약만 받는다. 읽은 파일 수십 개가 내 컨텍스트에 쌓이지 않는다. 실습 5에서 숫자로 본다.

컨텍스트가 80%를 넘기면 지시를 놓치거나 같은 실수를 되풀이하기 쉽다. 이 신호가 보이면 압축하거나 새로 시작한다. 실습 2에서 직접 채워 본다.

7. 심화: 기억

모델은 채팅이 끝나면 아무것도 기억하지 못한다. 새 채팅이 이전 일을 "아는" 것처럼 보이는 이유는 시작할 때 디스크의 파일을 다시 읽어 컨텍스트에 넣기 때문이다. 그래서 기억을 다룬다는 것은 어느 파일에 두고, 누가 그 파일을 볼 수 있게 하느냐를 정하는 일이다.

  1. 어디까지 기억하나: 그 채팅 안의 대화는 컨텍스트에 남고, 길어지면 요약된다(6장). 채팅 밖으로 이어지는 것은 파일에 적힌 것뿐이다.
  2. 어디까지 적용되나: 파일이 놓인 범위만큼이다. 저장소 안 파일은 저장소를 받은 모두에게, 사용자 폴더의 파일은 그 PC의 그 사람에게만 적용된다.
  3. 언제 읽나: 대부분 시작할 때 읽는다. 일부는 그 폴더 파일을 열 때, 지난 대화는 채팅을 이어 갈 때만 읽는다.

어디서 도느냐

같은 Claude, 같은 ChatGPT라도 어느 컴퓨터에서 도느냐에 따라 읽을 수 있는 기억이 완전히 달라진다. 브라우저냐 터미널이냐는 화면일 뿐이고, 기준은 파일을 읽고 명령을 실행하는 컴퓨터가 어디냐다. 아래에서 환경을 누르면 기억 → 생각과 실행 → 결과가 어느 컴퓨터를 거쳐 흘러가는지 차례로 보여 준다.

로컬에서도 생각하는 모델은 회사 서버에서 돈다. 내 PC에서 도는 것은 파일 읽기와 명령 실행 같은 도구뿐이다. 그래서 로컬에서도 읽은 파일 내용은 모델에게 보내진다.

새 채팅이 읽는 것

도구와 상황을 고르고 ▶ 새 채팅 시작을 누르면, 디스크의 파일이 읽히는 차례대로 컨텍스트 창으로 들어간다. 왼쪽 상자는 바깥일수록 넓은 범위다. 흐려진 파일은 그 상황에서 읽지 않고, 빗금 친 파일은 찾지 못한다.

클라우드 두 도구는 내 PC가 아니라 GitHub 저장소를 새로 클론한 컴퓨터에서 돈다. 그래서 저장소에 Push된 규칙 파일만 읽고, 내 PC의 사용자 폴더(~/.claude, ~/.codex)는 보지 못한다. 규칙을 고쳤다면 Push한 뒤 클라우드 작업을 시작한다.

Claude Code는 자동 메모리 폴더를 Git 저장소 단위로 정해서 하위 폴더와 worktree가 같은 메모리를 쓴다. 이 PC에서는 폴더 이름이 저장소 경로(c--Users-PC-Documents-GitHub-VScode-Practice)로 되어 있어서, 저장소 폴더를 옮기면 다른 메모리 폴더를 찾는다.

어디에 얼마나 남나

무엇Claude Code 로컬Claude Code 클라우드Codex 로컬Codex Cloud

사람마다 다른 값

예를 들어 읽기 권한만 받은 사람들이 저장소를 내려받아 쓰는데, 이름과 경로를 첫 채팅에서 물어보게 했다고 하자. 그 답을 어디에 두느냐로 다음 채팅의 결과가 갈린다.

새 채팅에서도
알아야 하는 값
PC마다 다른 값(이름, 경로)

묻지 말고 명령으로 알아내게 한다. 공용 AGENTS.md에 "git config user.name과 현재 작업 폴더에서 알아낸다"고 적으면 사람마다 자기 값이 나온다.

그 사람만 아는 값(역할, 호칭)

그 사람 PC의 ~/.claude/CLAUDE.md나 ~/.codex/AGENTS.md에 둔다. Cloud라면 채팅을 시작할 때 직접 넘긴다.

공용 저장소의 규칙 파일

읽기 권한이라 Push할 수 없고, 고쳐도 모두가 같은 값을 보게 된다. 개인 값을 두는 곳이 아니다.

저장소를 OneDrive 폴더에 두면 동기화와 Git이 같은 .git 파일을 함께 건드려 저장소가 깨질 수 있다. OneDrive 공유는 GitHub 권한과 별개라서, 공유받은 사람이 파일을 직접 고칠 수도 있다. 저장소는 OneDrive 밖에 두고 GitHub으로만 주고받는 편이 안전하다.

여러 환경을 위한 md 설계

사람마다 로컬, 클라우드, 일반 채팅을 섞어 쓰면 규칙 파일이 환경마다 흩어지기 쉽다. 아래 표는 기억이 놓인 곳마다 어느 환경에 닿는지를 보여 준다. 줄에 마우스를 올리면 그 기억이 닿는 환경만 밝아진다.

표에서 세 환경 모두에 닿는 칸은 채팅에 직접 넣은 글 하나뿐이다. 나머지는 환경마다 따로 이어 줘야 한다. 그래서 이 가이드는 원본 하나에서 환경마다 이어 붙이는 구조를 권한다.

  1. 원본은 저장소의 AGENTS.md 하나다. CLAUDE.md는 @AGENTS.md 한 줄만 둔다. 이렇게 하면 Claude Code와 Codex가 로컬과 클라우드에서 같은 규칙을 읽는다.
  2. 클라우드는 Push된 것만 읽는다. 규칙을 고쳤으면 Push한 뒤 클라우드 작업을 시작한다.
  3. 일반 채팅은 md를 스스로 읽지 않는다. 프로젝트 파일로 AGENTS.md를 올리고, 원본이 바뀌면 다시 올린다. 자동으로 맞춰지지 않는다.
  4. 개인 값은 저장소 밖에 둔다. 로컬은 ~/.claude/CLAUDE.md나 CLAUDE.local.md, 클라우드는 내 환경의 설정 스크립트, 일반 채팅은 계정 메모리나 맞춤 지침이다.
  5. 환경마다 다른 값은 규칙에 적지 않는다. 경로와 사용자 이름은 "명령으로 알아내라"고 적는다. 그러면 어느 환경에서 읽어도 맞는다.

8. 심화: 하네스

하네스는 모델을 둘러싼 모든 것이다. 모델에게 무엇을 보여 주고(컨텍스트), 무엇을 할 수 있게 하고(도구), 어디까지 허락하고(권한·샌드박스), 어떻게 확인하게 할지(검증)를 정한다. 같은 모델이라도 하네스가 좋으면 잘 쓰고, 나쁘면 같은 실수를 되풀이한다.

설계 원칙

  1. 권고와 강제를 나눈다. 지시문은 부탁이라 어길 수 있다. 꼭 지켜야 하는 것(비밀 파일 접근 금지, 검사 실행)은 권한 규칙이나 훅으로 막는다.
  2. 피드백 고리를 만든다. 에이전트가 스스로 틀렸음을 알 수 있어야 한다. 검사 명령 하나(npm run check)를 정하고, 수정할 때마다 돌리게 한다.
  3. 작게 열고 필요하면 넓힌다. 처음에는 읽기만, 다음에는 작업 폴더 쓰기만 허락한다. 네트워크나 폴더 밖 쓰기는 마지막이다.
  4. 지시문은 짧게, 근거는 파일로. 규칙 열 줄이 규칙 백 줄보다 잘 지켜진다.
  5. 결과를 남긴다. 결정과 다음 단계를 파일(STATUS.md)에 적어 다음 세션이 이어받게 한다.

이 저장소의 하네스

마스터의 저장소가 좋은 예다. AGENTS.md가 규칙을 말하고(권고), CLAUDE.md는 그것을 가져오고, npm run check가 링크, 문체, 폰트, 지도 데이터를 기계로 검사하며(검증), STATUS.md가 진행 상황을 남긴다(결과 기록). 규칙만 적은 것이 아니라 어긴 것을 잡아 주는 장치가 있다는 점이 핵심이다.

// Claude Code: .claude/settings.json - 파일을 고칠 때마다 검사를 자동으로 돌린다
{
  "hooks": {
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": "npm run check" }] }
    ]
  }
}

# Codex: ~/.codex/config.toml - 묻는 때와 닿는 범위를 따로 정한다
approval_policy = "on-request"
sandbox_mode    = "workspace-write"

9. 실습

명령어만 외우면 "개발자 노트에 왜 이런 게 적혀 있는지"를 알 수 없다. 아래 여섯 실습은 같은 요청을 설정 하나만 바꿔 돌려 보고, 무슨 일이 일어났는지, 무엇이 달라졌는지, 왜 해야 하는지를 보여 준다. 모두 이 페이지 안의 시뮬레이션이라 새로고침하면 처음으로 돌아가고 아무것도 저장되지 않는다.

실습 1지시문 한 줄이 결과를 바꾼다

같은 요청을 지시문 파일(CLAUDE.md/AGENTS.md)의 규칙만 바꿔 보낸다. 규칙을 켜고 끄면서 에이전트의 행동이 어떻게 달라지는지 본다.

왜 하나 지시문은 에이전트가 세션을 시작할 때 처음 읽는 규칙집이다. 매번 같은 말을 되풀이하지 않아도 되고, 사람이 바뀌어도 같은 방식으로 일하게 만든다. 규칙은 짧을수록 잘 지켜진다.

실습 2컨텍스트를 채우고 비운다

작업을 하나씩 추가해 컨텍스트가 차오르는 것을 보고, /compact와 /clear가 각각 무엇을 바꾸는지 눌러 본다. 숫자는 감을 잡기 위한 예시다.

왜 하나 컨텍스트가 가득 차면 느려지고 비싸지고, 앞에서 정한 규칙을 놓친다. 언제 압축하고 언제 새로 시작할지 아는 것이 긴 작업의 품질을 정한다.

실습 3권한 모드가 행동을 막고 푼다

같은 여섯 행동을 모드별로 돌려 본다. 어떤 행동은 그냥 지나가고, 어떤 행동은 허락을 구하고, 어떤 행동은 막힌다.

왜 하나 허락을 모두 열면 빠르지만 파일 삭제나 푸시도 그냥 지나간다. 모두 닫으면 안전하지만 매번 눌러야 한다. 일에 맞는 모드를 고르는 것이 하네스 설계의 시작이다. 이 표는 단순화한 모델이다.

실습 4훅과 검증이 실수를 되돌린다

에이전트가 오타가 든 수정을 했다고 하자. 검사 훅이 없을 때와 있을 때를 각각 재생해 결과를 비교한다.

왜 하나 "고쳤다"는 말은 증거가 아니다. 검사가 자동으로 돌고 실패가 에이전트에게 되돌아가야 스스로 고친다. 지시문의 "검사를 돌려라"는 부탁이고, 훅은 강제다.

실습 5서브에이전트로 컨텍스트를 아낀다

코드베이스에서 인증 코드를 찾는 탐색을 직접 할 때와 서브에이전트에게 맡길 때의 컨텍스트 사용량을 비교한다. 읽을 파일 수를 바꿔 본다.

왜 하나 탐색은 많이 읽고 조금만 남기는 일이다. 그 많은 읽기를 내 컨텍스트에 쌓을 필요가 없다. 요약만 받으면 본 작업에 쓸 자리가 남는다.

실습 6한 번만 실행해서 자동화한다

도구, 작업, 출력 형식, 권한 범위를 골라 claude -p와 codex exec 명령을 만든다. 각 부분이 무엇을 하는지 옆에 풀어 준다.

왜 하나 대화 없이 한 번 돌리면 CI, 스크립트, 예약 작업에서 쓸 수 있다. 사람이 없으니 권한은 최소로, 출력은 기계가 읽을 형식으로 정해야 한다.

12. 출처와 확인 방법

    이 페이지는 위 공식 페이지를 읽고 정리했다. 도구는 빠르게 바뀌므로 다음 순서로 직접 확인한다.

    1. 터미널에서 claude --version, codex --version으로 설치된 버전을 본다.
    2. 슬래시 명령은 /help로 지금 버전의 목록을 본다.
    3. 요금과 한도는 위 요금 페이지와 계정의 사용량 화면에서 본다.

    주석

    1. gpt-tokenizer 3.0.1(MIT 라이선스)을 tools/에서 npm으로 받아 guide/vendor/에 복사해 쓴다. o200k는 GPT-4o 이후 모델, cl100k는 GPT-4와 GPT-3.5가 쓰는 규칙이다. 한 글자가 여러 토큰으로 나뉘면 한 조각으로 묶고 오른쪽 위에 토큰 수를 적었다.
    2. 2026-11-26에 두 도구의 공식 GitHub 저장소(anthropics/claude-code, openai/codex의 README와 docs/install.md)와 Claude Code 설치 문서(code.claude.com/docs/en/setup)를 읽고 정리했다. Claude Code README에는 npm 설치가 더 이상 권장되지 않는다고 적혀 있다.
    3. README에는 Windows PowerShell 설치 명령이 있지만 docs/install.md의 지원 목록에는 Windows 11 + WSL2만 있다. WSL 없이 Windows에서 바로 돌릴 때 정식 지원인지는 확인 전이다.
    4. 2026-11-26에 Claude 도움말(Projects, 채팅 검색과 메모리), ChatGPT 도움말(Projects, Memory, 맞춤 지침), Claude Code 문서(on the web, desktop, cloud environments, settings), Codex Cloud 문서를 직접 읽고 정리했다. Claude 데스크톱 앱의 Code 탭은 세션마다 내 PC(로컬)와 클라우드 중에서 고른다. Codex Cloud는 저장소 없이도 시작할 수 있고, GitHub나 GitLab 저장소를 가져올 수 있다.
    5. 공식 문서의 권장안이 아니라, 위 표의 사실을 바탕으로 이 가이드가 정리한 구성이다.
    6. 2026-11-26에 Claude Code 문서(memory, how Claude Code works, Claude Code on the web, cloud environments, settings)와 Codex 문서(AGENTS.md, Memories, Cloud environments)를 직접 읽고 정리했다. Codex 문서 주소는 learn.chatgpt.com으로 옮겨져 있었다.
    7. 공식 문서는 "저장소 단위, worktree 공유"라고만 적었다. 폴더를 옮기면 새 메모리로 시작한다는 것은 이 PC의 폴더 이름에서 미루어 본 동작이며 확인 전이다. 문서에 따르면 autoMemoryDirectory 설정으로 위치를 고정할 수 있다.
    8. 읽은 Codex 문서에는 대화 기록의 저장 위치가 적혀 있지 않았다. ~/.codex/sessions/는 확인 전이다.
    9. 이 페이지의 요금, 한도, 버전, 변경 기록은 2026-11-24에 공식 페이지(Claude 요금제, Claude Code 변경 기록, Codex 요금제와 변경 기록)를 읽고 정리했다. 일부 페이지는 길어서 일부만 읽었고, 읽히지 않은 값은 ?로 표시했다.
    10. 표의 슬래시 명령은 2026-11-24 점검 기준으로 정리했다. 마스터가 실제 화면에서 직접 확인하기 전까지는 확인 전이다.
    11. 요금과 한도는 2026-11-24에 공식 페이지를 읽고 정리한 값이다. 페이지에서 읽히지 않은 칸은 ?로 두었고, 한도는 고정 수치가 아니라 추정치다. 결제 전에 공식 요금 페이지에서 다시 확인한다.
    12. Claude Code 변경 기록에 적힌 예고다. 검색 결과에는 Opus 4.8 빠른 모드가 11-30에 제거된다는 내용도 있었지만 공식 페이지에서 확인하지 못해 확인 전으로 둔다.
