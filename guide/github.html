1부 · 기본 작업

저장소를 만들고, PC와 GitHub 사이로 오가는 가장 기본 흐름이다. 이후 모든 부의 전제다.

1-1 GitHub 시작

확인 완료 · 비공개 연습 저장소 vscode-practice를 만들고, GitHub 웹에서 README.md에 메모를 남겼다. 회사에서는 VS Code를 열어 둔 상태다.

1-2 Clone·Push·Pull

GitHub는 프로젝트 파일과 Git 커밋을 온라인에 보관한다.

  • Clone은 저장소를 PC로 처음 복제한다.
  • Push는 PC의 커밋을 GitHub에 올린다.
  • Pull은 GitHub의 새 커밋을 받아 현재 브랜치에 반영한다.

1-3 다른 PC 작업

다른 PC(예: 집)의 VS Code에서는 처음 한 번 복제 단계대로 같은 저장소를 복제한다. 이미 복제했다면 그 폴더를 열고 Git: Pull을 실행한다. Windows 파일 탐색기에서 저장소 최상단의 index.html을 더블클릭하면 브라우저에서 이 가이드가 열린다.

Ctrl + S는 파일 저장, Commit은 버전 기록, Push는 GitHub에 올리기, Pull은 GitHub의 변경 가져오기다.

clone한 폴더를 다른 경로로 옮기기

다시 Clone할 필요 없이 폴더를 통째로 옮기면 된다. Git의 저장소 정보는 폴더 안의 숨김 폴더 .git에 모두 들어 있어서 이력과 원격 연결이 그대로 따라간다. 아직 Commit하지 않은 변경도 함께 옮겨진다.

  1. VS Code를 닫는다. 열려 있으면 폴더가 잠겨 옮겨지지 않는다.
  2. 파일 탐색기에서 폴더를 잘라내기(Ctrl + X)해 새 위치에 붙여넣는다(Ctrl + V).
  3. VS Code에서 파일 > 폴더 열기로 새 위치의 폴더를 연다. 소스 제어 화면의 변경 내용이 옮기기 전과 같으면 성공이다.

옛 경로는 VS Code의 최근 폴더 목록에 남으므로 새 경로로 다시 연다. 다시 Clone하는 방법도 있지만 Commit하지 않은 변경과 Push하지 않은 Commit은 새 폴더에 오지 않는다. 모두 Push한 것이 확실할 때만 쓰고, 옛 폴더는 확인한 뒤에 지운다.

2부 · 남의 코드 쓰기

다른 사람이 공개한 저장소를 가져와 쓰는 방법과 지켜야 할 조건이다. 1부의 Clone을 알면 된다.

2-1 남의 코드 쓰기

공개(Public) 저장소는 누구나 볼 수 있지만, 보인다고 마음대로 써도 되는 것은 아니다. 가져오는 방법은 GitHub의 버튼이 정하고, 써도 되는 범위는 그 저장소의 라이선스가 정한다. 라이선스는 만든 사람이 "이 조건을 지키면 써도 된다"고 적어 둔 허락서다.

가져오는 방법 고르기

하고 싶은 일방법특징
내 PC에서 실행하고 살펴본다Clone전체 이력이 함께 온다. 원본이 갱신되면 Pull로 받는다.
내 계정에 사본을 두고 고치거나, 원본에 수정을 제안한다Fork원본의 이력이 이어지는 사본이다. 풀 리퀘스트로 원본에 제안할 수 있다.
뼈대만 받아 새 프로젝트를 시작한다Use this template커밋 하나로 시작하는 새 저장소다. 원본과 이력이 이어지지 않는다. 버튼은 원본이 템플릿으로 설정한 경우에 쓴다.
지금 파일만 필요하다Code > Download ZIP그 시점의 파일만 받는다. 이력이 없어 Pull로 갱신할 수 없다.

Clone은 원본 저장소 화면의 Code 버튼에서 HTTPS 주소를 복사해 복제 단계대로 한다. 원본에 쓰기 권한이 없으면 내 Commit을 원본에 Push할 수 없다.

Fork는 다음 순서다.

  1. 원본 저장소 화면 오른쪽 위의 Fork를 누른다.
  2. Owner에서 사본을 둘 계정을 고른다. 이름과 설명은 바꿔도 된다.
  3. Create fork를 누른다. 화면 위의 저장소 이름이 내 계정 아래로 보이면 성공이다.
  4. 내 Fork를 Clone해 고치고 Push한다.

라이선스 확인하기

  1. 저장소 최상단에서 LICENSE, LICENSE.md, LICENSE.txt 파일을 찾아 연다. GitHub가 알아본 라이선스는 저장소 화면에 이름으로 표시되기도 한다.
  2. 파일이 없으면 README.md에 사용 조건이 적혀 있는지 본다.
  3. 폴더나 파일마다 조건이 다를 수 있으므로 README의 예외 안내, 이미지·글꼴·데이터의 출처 표시도 본다.

라이선스가 없으면 쓸 수 없다고 본다. 저작권은 기본으로 만든 사람에게 있어서, 허락 없이는 복제·배포·수정할 수 없다. GitHub 이용 약관상 공개 저장소를 GitHub 안에서 보고 Fork하는 것까지는 허용되지만, 그것이 내 프로젝트에 써도 된다는 뜻은 아니다. 쓰고 싶으면 Issue 등으로 만든 사람에게 라이선스를 추가해 달라고 요청하거나 허락을 받는다.

라이선스별 조건

아래 라이선스는 모두 상업적 사용, 수정, 배포, 개인 사용을 허용한다. 차이는 지켜야 할 조건이며, 모두 보증과 책임을 지지 않는다.

라이선스배포할 때 지킬 조건한 줄 요약
MIT, BSD-3-Clause저작권·라이선스 문구 포함조건이 가볍다. BSD-3-Clause는 원문의 이름 사용 제한 조항도 확인한다.
Apache-2.0문구 포함, 바꾼 사실 표시특허 사용 허락이 명시되어 있다. 상표 사용 권리는 주지 않는다.
MPL-2.0문구 포함, 바꾼 사실 표시, 소스 공개, 고친 파일은 같은 라이선스"같은 라이선스" 조건이 파일 단위다.
LGPL-3.0문구 포함, 바꾼 사실 표시, 소스 공개, 같은 라이선스(라이브러리)라이브러리로 가져다 쓰기만 하면 같은 라이선스 조건이 적용되지 않을 수 있다.
GPL-3.0문구 포함, 바꾼 사실 표시, 소스 공개, 수정본은 같은 라이선스이 코드를 바탕으로 만든 것을 배포하면 소스도 같은 조건으로 공개해야 한다.
AGPL-3.0GPL-3.0의 조건 + 네트워크 이용도 배포로 본다웹 서비스로만 제공해도 이용자에게 소스를 받을 권리가 생긴다.
Unlicense조건 없음저작권을 내려놓는 방식이다.

Creative Commons(CC) 라이선스는 글과 그림에 흔하다. CC는 소프트웨어에는 자기 라이선스를 쓰지 말라고 권한다. 문서나 이미지에 CC가 붙어 있으면 그 종류의 조건(출처 표시, 비영리 등)을 따로 확인한다.

쓸 때 지킬 것

  • 원본의 LICENSE 파일과 저작권 문구를 지우지 않는다. 코드 일부만 복사해 와도 출처와 라이선스를 남긴다.
  • 바꾼 사실을 표시해야 하는 라이선스는 변경 내용을 파일이나 문서에 적는다.
  • 여러 라이선스를 섞으면 서로 조건이 충돌할 수 있다. 배포 전에 package.json 등에 적힌 의존 패키지의 라이선스도 확인한다.
  • 비밀값이 섞여 있거나 정체를 모르는 설치 스크립트가 있을 수 있으므로, 실행하기 전에 README와 실행 명령을 읽는다.

내 저장소를 남이 쓰게 하려면 최상단에 LICENSE 파일을 둔다. 새 저장소를 만들 때 라이선스를 고르는 칸이 있고, 기존 저장소에는 파일을 직접 추가할 수 있다.

판단이 안 설 때
  • 혼자 공부하며 읽기만 한다: GitHub에서 읽고 Fork하는 것은 약관이 허용하는 범위다. 라이선스가 없으면 그 밖의 사용은 허락을 받는다.
  • 회사 업무나 판매 제품에 넣는다: 라이선스 이름만 보고 정하지 말고 회사의 규정과 담당자에게 확인한다.
  • 목록에 없는 라이선스나 직접 쓴 조건이 있다: 원문을 읽고, 해석이 안 되면 만든 사람에게 묻거나 쓰지 않는다.
3부 · 공개

만든 결과물을 웹 주소로 올린다. 1부만 끝나 있으면 된다. 남의 코드가 섞여 있으면 2부의 조건을 먼저 확인한다.

3-1 홈페이지 공개

진행 중 · 공개 전환과 Pages 설정까지 안내한 단계이며, 공개 주소로 접속해 확인하면 완료로 바꾼다.

GitHub Pages는 저장소의 HTML 파일을 누구나 열 수 있는 웹 주소로 공개하는 기능이다. 이 저장소는 루트의 index.html이 guide/vscode-guide.html로 이동시키므로 파일을 옮기지 않고 그대로 공개할 수 있다.

공개 순서

  1. 변경 사항을 모두 푸시한다. 소스 제어의 변경 사항이 비어 있어야 한다. 푸시하지 않은 내용은 공개 페이지에 나오지 않는다.
  2. 저장소를 공개(Public)로 바꾼다. GitHub 저장소의 Settings → General 맨 아래 Danger Zone에서 Change repository visibility → Make public을 누른다. 경고 창의 확인 버튼을 차례로 누르고, 마지막 입력칸에 계정이름/저장소이름 전체를 입력한 뒤 I understand, change repository visibility를 누른다.
  3. Pages를 켠다. Settings → Pages에서 Source를 Deploy from a branch로 두고, Branch는 main, 폴더는 / (root)를 골라 Save를 누른다.
  4. 배포를 기다린다. 1~2분 걸린다. 저장소의 Actions 탭에서 pages build and deployment 작업에 초록 체크가 뜨면 끝난 것이다.
  5. 주소를 확인한다. Settings → Pages 맨 위에 Your site is live at …와 함께 주소가 나온다. 형태는 https://계정이름.github.io/저장소이름/이다.
  6. 로그인하지 않은 상태로 열어 본다. 시크릿 창에 주소를 붙여넣어 「나의 개발 스텝」이 열리고 기술 연결 지도가 움직이면 성공이다. 404가 나오면 배포가 아직 끝나지 않았거나 푸시가 빠진 것이다.

무료 계정은 비공개 저장소의 Pages를 쓸 수 없으므로 2번의 공개 전환이 필요하다.

/ (root)와 /docs

Pages 설정의 폴더 선택은 사이트의 맨 위 폴더를 정한다.

옵션공개되는 범위시작 파일
/ (root)저장소 전체 (루트와 모든 하위 폴더)루트의 index.html
/docsdocs 폴더 안의 파일만docs/index.html

이 저장소의 홈페이지는 루트의 index.html과 guide/에 있고 docs/에는 블로그 초안만 있다. 따라서 / (root)를 골라야 한다. 저장소가 공개이면 /docs를 골라도 GitHub 저장소 화면에서는 모든 파일이 보이므로 숨기는 효과가 없다.

공개 전환이 안 될 때

공개 전환은 클릭 한 번으로 끝나지 않고 창이 여러 번 이어진다. 입력칸이 나오지 않으면 앞 단계 어딘가에서 멈춘 것이다.

  1. 경고 창이 길면 아래 버튼이 화면 밖에 숨는다. 브라우저를 Ctrl + -로 축소하고 창 안쪽을 스크롤한다.
  2. 창 안의 I have read and understand these effects 같은 확인 칸이나 버튼을 빠뜨리지 않았는지 본다. 버튼이 회색이면 앞 확인을 아직 누르지 않은 것이다.
  3. 마지막 입력칸에는 저장소 이름만이 아니라 계정이름/저장소이름 전체를 대소문자까지 정확히 입력한다.
  4. 브라우저의 자동 번역과 광고 차단 확장 프로그램이 창을 가릴 수 있다. 번역을 끄고 시크릿 창에서 다시 시도한다.
  5. 시크릿 창에서 로그인하지 않은 채 저장소 주소를 열어 본다. 열린다면 이미 공개 상태다.
  6. 포크이거나 조직 소유인 저장소는 공개 전환이 제한될 수 있다. 저장소 이름 위의 소유자 표시와 Fork 표시를 확인한다.
공개 후 알아둘 것
  • 공개한 기록은 되돌릴 수 없다. 나중에 비공개로 바꿔도 이미 복제되거나 캐시된 내용은 남을 수 있다. 무료 계정은 비공개로 돌리면 Pages도 꺼진다.
  • 공개 주소는 비밀이 아니다. 주소를 아는 사람은 누구나 열 수 있고 검색에도 노출될 수 있다.
  • 공개 저장소에서는 AGENTS.md를 포함한 모든 파일과 커밋 기록이 보인다. 비밀번호, 키, 토큰은 저장소에 넣지 않는다. 필요하면 .env 같은 파일에 두고 Git에서 제외한다.
  • 공개 전에 커밋 작성자 이메일이 GitHub 비공개용 주소(…@users.noreply.github.com)인지 확인한다. 이 저장소는 확인을 마쳤다.
4부 · 협업

다른 사람과 같은 저장소를 고치는 방법이다. 초대, 합치기 요청, 보호 규칙을 다룬다.

4-1 함께 작업

혼자 쓰던 저장소에 다른 사람을 들이는 가장 간단한 방법은 Collaborator(공동 작업자)로 초대하는 것이다. 소유권은 기존 계정에 그대로 남고, 초대받은 계정에는 코드를 고치고 올릴 권한만 생긴다. 내 계정의 저장소 목록에는 소유자/저장소이름 형태로 보인다.

초대하고 받기

  1. 소유자 계정으로 해당 저장소를 열고 Settings 탭의 Collaborators로 간다.
  2. Add people 버튼을 누르고 상대의 GitHub 아이디를 검색해 초대한다.
  3. 초대받은 사람은 자기 계정으로 이메일이나 GitHub 알림의 초대를 수락한다. 초대는 기간이 지나면 만료되므로 만료되면 소유자가 다시 보낸다.
  4. 수락하면 저장소를 Clone하고 수정한 뒤 Push할 수 있다. 성공하면 초대받은 사람의 목록에 소유자/저장소이름이 나타난다.

개인 계정 소유 저장소의 공동 작업자는 읽기만 하는 권한으로 만들 수 없다. 초대받으면 코드를 올릴 수 있는 쓰기 권한이 생긴다. "이 사람은 보기만", "이 사람은 관리까지"처럼 권한을 나눠야 한다면 다음 장의 Organization이 필요하다.

풀 리퀘스트로 합치기

Pull Request(PR, 풀 리퀘스트)는 "내가 고친 브랜치를 main에 합쳐 달라"고 GitHub에서 요청하는 기능이다. 합치기 전에 다른 사람이 바뀐 줄을 보고 의견을 달고 승인하는 자리이기도 하다. Git이 아니라 GitHub가 제공하는 기능이다. 공동 작업자가 생기면 main을 바로 고치지 않고 이 방식으로 합치는 것이 기본이다.

  1. 내 컴퓨터에서 새 브랜치를 만들고 파일을 고친 뒤 Commit하고 Push한다.
  2. GitHub 저장소 화면에 노란 띠로 Compare & pull request 버튼이 뜬다. 눌러서 PR 만들기 화면을 연다. 띠가 없으면 위쪽 Pull requests 탭의 New pull request를 쓴다.
  3. 합칠 대상이 main, 내 브랜치가 비교 대상인지 확인하고 제목과 설명을 쓴 뒤 Create pull request를 누른다.
  4. 리뷰어가 Files changed에서 바뀐 줄(git diff와 같은 모양)을 보고 승인(Approve)하거나 수정을 요청한다.
  5. 승인되면 Merge pull request를 눌러 합친다. 성공하면 PR이 보라색 Merged 상태가 되고 main에 변경이 들어간다.

혼자 쓰는 연습 저장소에서는 PR 없이 main에 바로 Push해도 된다. 다른 사람의 저장소에 기여할 때는 먼저 Fork(내 계정으로 복사)하고, 거기서 고친 뒤 원본으로 PR을 보낸다.

main 브랜치 보호하기

Branch protection(브랜치 보호)은 main 같은 중요한 브랜치에 "이 조건을 지켜야만 합쳐진다"는 문을 다는 기능이다. 조직 화면에서 "코드 리뷰를 강제하여 브랜치를 보호하세요"라고 안내하는 것이 이것이다. 보호가 없으면 Write 권한이 있는 사람은 누구나 main에 바로 Push할 수 있다. 보호를 켜면 모두가 PR을 거쳐야 한다.

안내문의 두 용어는 이렇게 읽는다. 브랜치 이름 패턴(Branch name pattern)은 어느 브랜치를 보호할지 정하는 이름 칸이고 main이라고 쓴다. 병합 전 풀 리퀘스트 필요(Require a pull request before merging)는 직접 Push를 막고 PR로만 합치게 하는 체크 항목이다.

  1. 저장소 화면 위쪽의 Settings → Branches를 연다. 새 화면에서는 Rules → Rulesets에 같은 기능이 있다.
  2. Add branch protection rule을 누르고 Branch name pattern에 main을 쓴다.
  3. Require a pull request before merging를 체크한다. 팀이라면 Require approvals를 켜고 승인 인원을 1명 이상으로 정한다.
  4. 자동 검사가 있으면 Require status checks to pass도 체크한다. 이 저장소의 npm run check 같은 검사를 Actions로 돌릴 때 쓴다.
  5. 맨 아래 Create(또는 Save changes)를 누른다. 성공하면 main에 직접 Push했을 때 거부 메시지가 나오고, PR 화면에는 승인이 없으면 병합 버튼이 막힌다.

  • 관리자(Admin)는 기본으로 규칙을 우회할 수 있다. 관리자도 막으려면 우회를 허용하지 않는 항목을 켠다.
  • 혼자 쓰는 연습 저장소에는 필요 없다. 규칙을 켜면 나도 PR을 거쳐야 해서 번거롭다.
  • AI 에이전트에게 저장소를 맡길 때도 쓸모가 있다. 에이전트가 main에 바로 Push하지 못하고 PR로만 올리게 막는 안전장치다. AI 페이지의 하네스에서 말한 "사람이 확인하는 자리"를 GitHub 쪽에서 강제하는 방법이다.
  • 무료 조직의 비공개 저장소에서는 이 기능을 쓸 수 없다. 유료 플랜이 필요하다는 점은 5-1장에서 다룬다.
외부 앱 접근 문제

초대를 수락했는데도 외부 앱의 저장소 선택 화면에 목록이 비어 있는 경우가 있다. 앱이 그 저장소에 접근할 권한을 받지 못해서다.

  1. 저장소 소유자 계정으로 GitHub의 Settings → Applications → Installed GitHub Apps로 간다.
  2. 해당 앱 옆의 Configure를 누른다.
  3. Repository access에서 Only select repositories를 고르고 해당 저장소를 추가한 뒤 저장한다.
  4. 앱이 아직 설치되어 있지 않으면 소유자 계정에 먼저 설치한다. 성공하면 앱을 새로 고쳤을 때 저장소가 목록에 보인다.

저장소가 조직 소유이면 같은 설정이 조직의 Settings 안에 있다.

초대가 안 먹을 때
  1. 초대 메일이 없으면 스팸함과 GitHub 알림(종 모양)을 본다.
  2. Push가 거부되면 상대가 초대를 수락했는지, 저장소 주소가 맞는지 확인한다.
  3. 조직 저장소라면 아래 5-1장의 역할과 SSO 항목도 함께 본다.
5부 · 조직 운영

사람과 저장소가 많아질 때 쓰는 Organization이다. 4부의 초대보다 한 단계 큰 단위다.

5-1 조직과 권한

Organization(조직)은 여러 사람이 저장소를 함께 가지는 공용 계정이다. 개인 계정과 달리 사람이 아니라 조직이 저장소의 주인이 되고, 멤버마다 역할을 따로 줄 수 있다. 사람마다 할 수 있는 일을 다르게 정하려면 Organization이 사실상 필수다. 팀 프로젝트, 동아리, 회사 일처럼 주인이 바뀌어도 저장소가 남아야 할 때도 쓴다.

저장소를 묶는 상자

Organization은 저장소의 한 종류가 아니다. 저장소를 담는 계정이다. 내 개인 계정 아래에 저장소가 여러 개 있듯이, 조직 아래에도 저장소가 여러 개 들어간다. 저장소 자체는 그대로 파일과 커밋 기록이 있는 같은 저장소다. 달라지는 것은 주인과 관리 방식이다.

개인 계정의 저장소조직의 저장소
주소github.com/내아이디/저장소github.com/조직이름/저장소
주인나 한 사람조직(사람이 바뀌어도 저장소는 그대로)
권한 주는 법저장소마다 공동 작업자를 하나씩 초대, 쓰기 권한뿐조직에 멤버를 두고 Read, Write, Admin 같은 역할로 나눔. 팀 단위로 한 번에 줄 수 있음
결제와 요금제내 계정조직 단위(저장소가 몇 개든 한곳에서 관리)
사람이 떠나면저장소와 권한 정리를 직접 해야 함멤버만 빼면 되고 저장소는 조직에 남음

구조는 이렇다. 조직 my-team 아래에 web, api, docs 저장소가 있고, 멤버 a, A, b, c가 조직에 속한다. 멤버마다 저장소별로 역할이 다를 수 있다. 예를 들어 b는 web에서는 Write이고 api에서는 Read다.

Settings는 두 곳이다

헷갈리기 쉬운 부분이다. 조직을 쓰면 Settings가 두 단계로 나뉜다.

위치들어가는 법여기서 하는 일
조직 Settings조직 화면(github.com/조직이름) 위쪽의 Settings멤버 초대와 제거, 팀 만들기, 멤버 기본 권한, 2단계 인증 필수, 결제와 요금제. 조직 전체에 적용된다
저장소 Settings조직 안의 저장소 화면 위쪽의 Settings그 저장소 하나의 공개 여부, 브랜치 규칙, 누구에게 어떤 역할을 줄지(Collaborators and teams)

이 장의 "조직 소유 저장소의 Settings"는 아래쪽, 즉 저장소 Settings를 뜻한다. 사람을 조직에 들이는 일은 조직 Settings, 그 사람이 이 저장소에서 할 수 있는 일을 정하는 일은 저장소 Settings에서 한다. 순서는 조직에 초대하고, 저장소에서 역할을 주는 것이다.

저장소를 조직 안에 만든다고 코드 작성 방법이 바뀌지는 않는다. Clone, Commit, Push, Pull은 개인 저장소와 똑같다. 바뀌는 것은 주소, 주인, 권한과 결제다.

상황알맞은 방법
친구 한두 명이 같이 고친다4-1장의 공동 작업자 초대면 충분하다
누구는 읽기만, 누구는 쓰기, 누구는 관리까지 나눈다Organization 소유로 두고 역할을 준다
사람이 바뀌어도 저장소가 남아야 한다Organization 소유로 두고 Owner를 여러 명 둔다

무료로 만들기

  1. GitHub 오른쪽 위의 + 버튼에서 New organization을 고른다.
  2. 요금제 선택 화면에서 Free를 고른다.
  3. 조직 이름(계정 이름처럼 주소가 되므로 이미 쓰는 이름은 안 된다)과 연락용 이메일을 넣고, 이 조직이 My personal account인지 A business or institution인지 고른다.
  4. 멤버를 초대하는 화면에서 아이디나 이메일로 사람을 추가한다. 나중에 해도 된다. 성공하면 github.com/조직이름 화면이 열리고 내가 Owner(소유자)로 보인다.
  5. 저장소는 조직 화면의 New repository로 새로 만들거나, 아래 방법으로 기존 개인 저장소를 옮겨 온다.
지금 저장소가 개인 계정 소유일 때
  1. 개인 계정 저장소에서는 공동 작업자에게 Read만 따로 줄 수 없다.
  2. 위 순서로 Organization을 만든다.
  3. 6-1장의 저장소 소유권 넘기기 순서로 저장소를 그 조직에 이전한다.
  4. 이전한 뒤 조직 저장소에서 역할을 지정한다. 이 일은 되돌리기 어려우니 조직 이름과 사람 목록을 먼저 정해 둔다.

역할 나누기

비공개 저장소를 조직 소유로 두면 사람마다 권한을 따로 줄 수 있다. 예를 들어 소유자 a, 관리자 역할의 A, 읽기만 하는 직원 b와 c가 있는 구성이다.

계정역할할 수 있는 일
aOrganization Owner조직과 저장소 전체 관리
A저장소 Write 또는 AdminWrite는 Pull과 Push, Admin은 여기에 초대와 권한 관리까지
b, c저장소 Read열람, Clone, Pull. 원격 저장소에 Push는 못 한다
  1. 먼저 사람이 조직에 들어와 있어야 한다. 조직 Settings에서 멤버로 초대한다.
  2. 조직 안의 해당 저장소 Settings에서 Collaborators and teams를 연다.
  3. Add people으로 사람을 찾아 초대하고 역할을 고른다. a가 A에게 Admin을 주면 A가 직접 b와 c를 Read로 초대할 수 있다.
  4. 이미 조직 멤버라면 팀이나 조직 기본 권한으로 Write가 이미 주어져 있는지 먼저 확인한다. 같은 사람이 여러 경로로 권한을 받으면 더 높은 쪽이 적용된다.

성공하면 Collaborators and teams 목록에 사람과 역할이 나란히 보인다. Read인 b가 Push를 시도하면 거부 메시지가 나오는 것이 정상이다.

처음 정해 두면 좋은 것
  1. Owner는 두 명 이상으로 둔다. 한 명뿐일 때 계정을 잃으면 조직을 관리할 사람이 없다.
  2. 멤버 기본 권한(Base permissions)을 Read로 시작하고 필요한 사람에게만 Write를 준다.
  3. 조직 설정에서 2단계 인증 필수를 켠다. Free에서도 쓸 수 있다.
  4. 사람마다 따로 주기 번거로우면 Team(그룹)을 만들어 팀 단위로 역할을 준다.

  • 회사 계정으로만 로그인하게 묶거나 사람 계정을 한 번에 만들고 지우려면 Enterprise가 필요하다.
권한이 안 먹을 때
  1. Push가 거부되면 내 역할이 Read나 Triage인지 Owner나 Admin에게 확인한다.
  2. Admin 메뉴가 안 보이면 Admin 권한이 없는 것이다. 역할 상향을 부탁한다.
  3. 조직이 SSO(회사 로그인으로 묶는 인증)를 켜 둔 경우, 내 토큰과 로그인을 조직에 승인해야 접근된다.
6부 · 저장소 관리

드물게 하지만 되돌리기 어려운 작업이다. 소유권을 넘기고, 지우고, 되살린다.

6-1 소유권 이전

저장소의 주인을 다른 계정이나 조직으로 옮기는 기능이 Transfer ownership(소유권 이전)이다. 파일과 커밋 기록, 이슈, PR, 스타, 협업자는 그대로 함께 간다. 복사본을 만드는 Fork와 달리 원본이 통째로 옮겨 간다.

하고 싶은 일쓰는 방법
다른 사람이 같이 고치게 한다공동 작업자로 초대한다(소유권은 그대로)
내 계정에서 조직으로 옮긴다소유권 이전, 받는 곳에 조직 이름을 입력한다
저장소를 완전히 다른 사람에게 준다소유권 이전, 받는 곳에 상대 계정 이름을 입력한다

이전 순서

  1. 보내는 쪽은 저장소의 관리자(Admin) 권한이 있어야 한다. 저장소 화면 위쪽의 Settings 탭을 연다.
  2. General 화면을 맨 아래까지 내려 빨간 테두리의 Danger Zone을 찾는다.
  3. Transfer ownership의 Transfer 버튼을 누른다.
  4. 새 주인의 계정 이름이나 조직 이름을 입력한다. 받는 쪽에 같은 이름의 저장소가 이미 있으면 진행되지 않는다. 필요하면 이름 칸에서 새 저장소 이름을 바꾼다.
  5. 확인 칸에 계정이름/저장소이름 전체를 정확히 입력하고 이전을 확정한다.
  6. 받는 쪽이 개인 계정이면 이메일로 확인 요청이 가고, 받는 사람이 정해진 기간 안에 수락해야 이전이 끝난다. 조직이면 조직에서 저장소를 만들 수 있는 사람이 받아야 한다. 요청을 보낸 뒤에는 상대에게 이메일을 확인해 달라고 알린다.

이전이 끝나면 저장소 주소가 github.com/새주인/저장소이름으로 바뀐다. 성공하면 저장소 화면 위쪽의 소유자 이름이 새 주인으로 보인다.

이전 후 해야 할 일
  • 이전 주소는 한동안 새 주소로 자동 연결된다. 그래도 내 컴퓨터의 연결 주소는 바꿔 두는 편이 낫다. 터미널에서 git remote -v로 지금 주소를 보고 git remote set-url origin https://github.com/새주인/저장소이름.git으로 바꾼다. 새 주인이 같은 이름으로 저장소를 다시 만들면 자동 연결이 끊긴다.
  • GitHub Pages 주소는 자동 연결되지 않는다. 계정.github.io/저장소 주소가 새 주인 기준으로 바뀌므로 README와 북마크의 주소를 고친다. 이 저장소처럼 Pages로 공개한 경우 새 주인이 Settings의 Pages에서 공개 설정을 다시 확인한다.
  • 이전한 뒤에는 내 쪽의 관리자 권한이 사라질 수 있다. 계속 같이 작업하려면 새 주인에게 협업자로 초대해 달라고 요청한다.
  • 내 계정에서 만든 Fork나 Actions 비밀값(Secrets) 같은 연결 설정은 저장소 종류에 따라 다르게 동작할 수 있다. 이전 직후 Settings와 Actions 탭을 한 번 훑어 확인한다.
  • 코드 안에 옛 주소(github.com/옛주인/…)가 적힌 곳, 예를 들어 README.md와 배포 설정을 검색해서 새 주소로 고친다.
이전이 안 될 때
  1. Transfer 버튼이 보이지 않으면 Admin 권한이 없는 것이다. 저장소 주인이나 조직 관리자에게 부탁한다.
  2. 받는 쪽에 같은 이름의 저장소나 Fork가 있으면 막힌다. 이름을 바꾸거나 받는 쪽의 저장소를 정리한다.
  3. 조직으로 보낼 때는 받는 쪽이 정책으로 이전을 제한했을 수 있다. 조직 관리자에게 허용 여부를 묻는다.
  4. 수락 메일이 오지 않으면 스팸함을 본다. 기간이 지나면 요청이 만료되므로 처음부터 다시 보낸다.
  5. 이전은 돌이키기 어렵다. 잘못 보냈다면 새 주인에게 같은 방식으로 다시 이전해 달라고 부탁해야 한다. 보내기 전에 계정 이름의 철자를 한 번 더 확인한다.

6-2 삭제와 복구

저장소와 Organization은 지울 수 있다. 지우기 전에 더 가벼운 대안이 있는지 먼저 본다. 여기서 말하는 조직은 4-1장과 5-1장의 Organization이다. 여러 조직을 묶는 Enterprise 계정은 다루지 않는다.

하고 싶은 일알맞은 방법되돌리기
더 이상 안 쓰지만 기록은 남기고 싶다저장소 Settings → General의 Archive this repository(읽기 전용으로 보관)쉬움(보관 해제)
다른 사람이나 조직에 넘기고 싶다6-1장의 소유권 이전어려움(상대가 다시 이전해야 함)
저장소 하나를 없애고 싶다저장소 삭제90일 안에 일부 가능
조직을 없애고 싶다조직 삭제GitHub가 내용을 복구하지 못한다고 안내

저장소 삭제

조직 Owner이거나 그 저장소의 Admin 권한이 있으면 지울 수 있다. 조직이나 Enterprise 정책이 삭제를 막아 두었으면 Admin이어도 버튼이 동작하지 않을 수 있다.

  1. 저장소 화면 위쪽의 Settings → General을 열고 맨 아래 Danger Zone으로 내려간다.
  2. Delete this repository를 누르고, 이어지는 창에서 I want to delete this repository와 I have read and understand these effects를 차례로 누른다.
  3. 저장소 이름을 정확히 입력하고 Delete this repository를 누른다. 성공하면 저장소 주소가 열리지 않고 내 저장소 목록에서 사라진다.

저장소를 지우면 생기는 일

  • Fork: 공개 저장소를 지워도 그 Fork는 남는다. 비공개 저장소를 지우면 Fork도 모두 함께 지워진다.
  • 팀 권한: 팀에 준 저장소 권한이 영구히 지워지고 되돌릴 수 없다. 저장소를 복구해도 팀 권한은 돌아오지 않으므로 다시 줘야 한다.
  • 내 컴퓨터의 Clone: 문서에는 적혀 있지 않다. Git은 폴더 안에 기록을 통째로 갖고 있어서, 이미 받은 폴더는 보통 그대로 남는다. 그래서 지우기 전에 Pull로 최신으로 받아 두면 백업이 된다.
  • 공개한 Pages 주소, 이슈, PR, 별, Wiki, Actions, 연결된 앱이 어떻게 되는지는 이 문서에 적혀 있지 않다. 저장소 자체가 사라지므로 함께 쓸 수 없게 된다고 보고, 필요하면 미리 내려받는다.
지운 저장소 되살리기
  1. 삭제 후 90일 안이면 일부 저장소는 되살릴 수 있다. 삭제 직후에는 최대 한 시간 정도 지나야 복구 목록에 나타난다.
  2. 개인 계정은 Settings → Repositories → Deleted repositories에서, 조직은 조직 Settings의 Deleted repositories에서 Restore를 누른다.
  3. I understand, restore this repository를 누른다. 성공하면 저장소가 다시 목록에 보인다.
  4. Fork 묶음(원본과 Fork들의 연결)이 비어 있지 않으면 복구되지 않는다. 다른 Fork를 모두 지우거나 떼어 내야 하고, 그래도 안 되면 유료 요금제에서만 GitHub Support에 요청할 수 있다.
  5. 첨부 파일과 릴리스 같은 세부 항목이 복구되는지는 문서에 적혀 있지 않다.

조직 삭제

  1. 오른쪽 위 프로필 사진 → Your organizations에서 지울 조직을 고른다.
  2. 조직 화면의 Settings → Danger zone의 Delete this organization을 누른다.
  3. 조직 이름을 입력하고 Cancel plan and delete the organization을 누른다. 문서에는 어느 역할이 지울 수 있는지가 적혀 있지 않으니, 보통 Owner가 한다고 보고 Owner에게 확인한다.

조직을 지우면 생기는 일

  • 조직의 모든 저장소, 비공개 저장소의 Fork, Wiki, 이슈, PR, 프로젝트와 조직 페이지가 영구히 지워진다. 문서는 이 일이 되돌릴 수 없고 GitHub도 내용을 복구하지 못한다고 안내한다. 저장소 삭제와 달리 90일 복구에 기댈 수 없다.
  • 조직의 결제가 끝난다. 환불이나 일할 계산이 어떻게 되는지는 문서에 적혀 있지 않다.
  • Packages와 컨테이너 이미지가 함께 지워진다. 그 패키지에 기대는 다른 프로젝트가 깨질 수 있다고 문서가 경고한다.
  • 이름이 90일 동안 잠긴다. 그 기간에는 다른 조직이나 개인 계정이 같은 이름을 쓸 수 없고, 지나면 자동으로 풀린다. 이름을 바로 쓰고 싶다면 지우는 대신 이름을 바꾼다.
  • 영구히 쓸 수 없는 이름이 생길 수 있다. 공개 저장소가 Marketplace 액션이거나 지난 한 주 동안 복제 100회 또는 Actions 사용 100회를 넘었으면 "소유자 이름과 저장소 이름" 조합이 영구히 폐기된다. 공개 컨테이너 이미지가 다운로드 5,000회를 넘었으면 전체 이미지 이름이 폐기된다.

계정에 패널티가 있나

공식 문서 세 쪽에는 저장소나 조직을 지웠다고 내 계정에 주어지는 불이익(경고, 제한, 신용 감소 같은 것)이 적혀 있지 않다. 그래서 정해진 패널티는 확인하지 못했다. 다만 실제로 따라오는 불이익은 있다.

  • 되돌릴 수 없는 데이터 손실(조직은 특히 그렇다)
  • 이름이 90일간 잠기거나, 일부는 영구히 못 쓰게 됨
  • 내 저장소나 패키지에 기대던 다른 사람의 프로젝트가 깨지는 일
  • 결제를 끝낸 뒤 환불이 안 될 수 있음. 정확한 규정은 결제 화면과 GitHub 지원에서 확인한다.
지우기 전에 확인할 것
  1. 저장소는 git pull로 최신을 받은 폴더를 따로 복사해 둔다. 이슈와 PR은 Clone에 들어 있지 않으니 필요한 글은 따로 저장한다.
  2. 4-1장의 협업자와 5-1장의 팀에게 지운다고 알리고, 이 저장소를 가리키는 주소(README, 배포 설정, 다른 프로젝트의 의존)를 찾아 둔다.
  3. 조직이면 Packages와 Actions가 다른 곳에서 쓰이고 있는지 확인한다.
  4. 정말 없애는 것이 목적인지, 보관(Archive)이면 충분한지 다시 묻는다.
  5. 비밀값이 저장소에 들어간 적이 있다면 지우는 것으로 끝내지 말고 그 키를 발급받은 서비스에서 폐기한다.

주석

  1. 2026-11-25에 GitHub 문서(라이선스 지정, 이용 약관 D.5, Fork, 템플릿, 소스 내려받기), choosealicense.com, Creative Commons FAQ를 읽고 정리했다. 요약이며 법률 자문이 아니다. 실제 조건은 해당 저장소의 라이선스 원문이 우선한다.
  2. choosealicense.com의 표는 BSD-3-Clause의 이름 사용 제한을 따로 표시하지 않았다. 해당 조항은 원문에서 직접 확인한다.
  3. 무료 계정의 비공개 저장소는 Pages를 쓸 수 없는 것으로 알려져 있다. 정책은 바뀔 수 있으니 결제 전에 Settings → Pages 화면의 안내를 직접 확인한다.
  4. 초대가 만료되는 기간의 정확한 일수는 문서에서 확인하지 못했다. 메일이나 알림에 만료 안내가 있으면 그것을 따른다.
  5. 메뉴 이름은 GitHub 화면 개편으로 달라질 수 있다. 예를 들어 Collaborators and teams가 Collaborators & teams로 보이는 화면도 있다. 안 보이면 비슷한 이름(Applications 등)을 찾는다. 이 장의 메뉴 경로는 마스터가 실제 화면에서 확인하기 전까지 확인 전이다.
  6. 2026-11-24에 GitHub 요금 페이지와 공식 문서 두 쪽(요금제, 조직 소개)을 읽어 정리했다. 두 곳 모두 화면에 "마지막 갱신일"이 없다. 요금과 포함량은 바뀔 수 있다.
  7. 관리자 우회 항목의 이름은 화면 버전에 따라 다르다(예전에는 Include administrators, 지금은 우회를 허용하지 않는다는 뜻의 항목). 이 장의 이름과 위치는 마스터가 실제 화면에서 확인하기 전까지 확인 전이다.
  8. 공개 저장소는 무료로 쓸 수 있고, 비공개 저장소는 유료 플랜(5-1장의 Team 이상)에서 열리는 것으로 요금 문서에 적혀 있다. 무료 개인 계정의 비공개 저장소 조건은 확인하지 못했다. 조직 화면의 "코드 리뷰를 강제하여 브랜치를 보호하세요" 안내가 이 기능이다.
  9. 가격은 사용자 1명당 월 기준이며 요금 페이지에 적힌 값이다. 결제하기 전에 GitHub 요금 페이지를 다시 확인한다.
  10. 요금 페이지는 Actions를 분 단위(Free 2,000분, Team 3,000분, Enterprise 50,000분)로, 공식 문서는 포함 사용액(Free $12, Team $18, Enterprise Cloud $300)으로 적어 두 곳이 서로 다르게 보인다. 두 쪽이 어떻게 이어지는지는 문서에 적혀 있지 않다. 실제 청구는 결제 화면에서 확인한다.
  11. 2026-11-24에 GitHub 공식 문서 세 쪽(저장소 삭제, 저장소 복구, 조직 삭제)을 읽어 정리했다. 문서에 적혀 있지 않은 항목은 "적혀 있지 않다"고 밝혔고, 추측으로 채우지 않았다.
  12. 조직 복구 문서는 열리지 않아서 복구 가능 여부와 기간을 확인하지 못했다. 확인 전이므로 복구되지 않는다고 보고, 지우기 전에 반드시 백업한다.
